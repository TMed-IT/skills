# UIの設計と改善

このskillのルールは、すべての製品に適用するUIの必須仕様であり、デザインテストの合否基準として扱う。各ルールが対象とする操作や状態がある場合は、必ず満たす。特定のフレームワークやCMSを前提にしない。

## 適用の順序

- 対象プロジェクトの指示とデザイン規約、既存の共通部品、実際に適用されるトークンを先に確認する。既存のデザインや部品を使う場合も、このskillの必須仕様を満たすように整える。ブランド、画像の有無、フォント、FAQの開閉方式、Selectの採用などは持ち込まない。
- [UIの実装・確認パターン](references/ui-patterns.md)のうち、変更する操作や画面に関係する節を読む。
- 日本語のUI文言を作成・修正する場合は、[japanese-ui-writing](../japanese-ui-writing/SKILL.md)を併用する。
- 見た目の調整ではCMSの編集属性、認証、公開範囲、キャッシュ、フォームの入力保持を保つ。別の用途の管理画面へテーマを漏らさない。

## 基本の方針

- 処理中は対象のボタンや領域にスピナーを出し、寸法と操作名を保つ。進捗文言や内部ステータスをそのまま表示しない。製品が進捗量や処理段階を必要とする場合は、その仕様を優先する。
- 開始・終了を読み上げでも伝え、失敗・空・完了・権限の状態を待機表示と区別する。結果不明の更新を自動で再実行しない。
- 保存・削除・送信などの操作結果の通知は、成功・失敗ともに共通のtoastに統一する。インラインの通知バーやメッセージを重ねない。入力項目ごとのエラーと、空・取得失敗・権限などの継続する状態説明は該当箇所に残す。
- 同じ役割の見出し、文字、余白、角丸、操作部品は共通の値を使う。ページごとの近似値の追加より、共通部品で揃える。固定のpx値を別の製品から移植しない。
- 主な操作を明確にし、補助操作を整理する。実データと意味のある状態は残し、装飾用の連番や反復ラベルを増やさない。
- ダイアログは内部のTab移動、Escape、フォーカス復帰、背面の操作とスクロールの固定を扱う。重ねた場合も最後のダイアログを閉じるまで固定する。

## 変更後の確認

変更した画面と状態を実際に操作し、関係する各ルールをデザインテストの確認項目として合否を判定する。不適合は修正してから再確認する。狭い画面と広い画面、長い名称、空・成功・失敗・処理中を確認し、文字切れ、横スクロール、配置の変化を調べる。キーボード操作と動きを減らす設定への対応を確認し、ライト・ダークは製品が対応する各モードで確認する。

文字200％、長い名称、ソフトウェアキーボード表示時にも、主要情報と確定操作への到達性を確認する。共通部品の変更時は、代表的な利用画面も確認する。

確認できた範囲、未確認の範囲、未解消の不適合を分けて報告する。未確認や不適合を合格として扱わず、レビューで見つけた候補を修正済みと扱わない。
